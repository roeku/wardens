# Engine choice: Rust where it pays, the browser where it pays

## Recommendation
**Write the simulation in Rust and the view in TypeScript with three.js (WebGL2).**
- The Rust crate compiles to WebAssembly for the browser, and natively for the headless harness.
- **Don't write the renderer in Rust for this hackathon:** not Bevy, not raw wgpu, not macroquad.
- **Fallback:** if the Rust/WASM toolchain is still fighting you at the end of day 1, write the simulation in TypeScript instead. The spec is language-neutral and the original was all TypeScript.

### Why not all-Rust
| Concern | All-Rust renderer (Bevy / wgpu) | Rust sim + three.js view |
|---|---|---|
| **Judges need a live link**, and they rank the demo on how it holds up live | Possible via WASM, but builds are 10–30 MB, and WebGPU/WebGL2 backend quirks differ by browser and phone | Plain web page; works on phones; the original already ran at 92/100 on an old phone |
| **The look** (`02-look.md`) | Every part needs custom render-graph work: the low-res art-pixel target, outlines from depth, the night pass, toon ramp, Bayer dither. Bevy's render-graph API changes every release, and coding models often write outdated Bevy code | The spec describes this pipeline in three.js terms, almost line by line |
| **Voice, audio, input** | Microphone, Web Audio and pointer events go through `web-sys` bindings, which is verbose and slower to debug | Native browser APIs |
| **Speed of iteration over 8 days** | Rust compile times plus WASM rebuilds slow every visual tweak | Vite hot reload for the view; Rust rebuilds only when rules change |
| **What the AI coding agent is best at** | Weakest: Rust graphics APIs | Strongest: TypeScript + three.js; Rust for plain logic is fine |

### Where Rust genuinely wins
1. **Determinism you can trust.** The original noted that lockstep across browsers was risky because `Math.sin` and friends may differ between JS engines. In Rust, use the `libm` crate for every transcendental function, so the same code gives bit-identical results natively and in WASM. Replays, tests and any future multiplayer get easier.
2. **A fast native harness.** The original's balance sweeps (20–30 campaigns per measurement) were slow in Node. Native Rust runs hundreds of campaigns in seconds, so balancing progression (`07-progression.md` §10) becomes practical in the time you have.
3. **Heavy CPU work:**
   - soldiers stepping at 30 Hz
   - the neighbour grid and A*
   - map generation
   - ground painting (about 1,000 × 750 texels)

   These run faster in WASM than in JS, with no garbage-collection pauses.
4. **Technical depth for the judges.** One rules crate runs in three places: the browser, the native test harness, and server-side validation if you want it. That is a clean story.

### The boundary between Rust and TypeScript
The rule from the original holds: **the simulation never reads the view, and the view never writes to the simulation.** Every change goes through orders.

**Rust to TypeScript, every frame (zero copy):**
- The sim keeps **packed per-soldier and per-squad records** (fixed-size f32 and u32 arrays, layout in `contracts`) in WASM memory.
- TypeScript makes `Float32Array` and `Uint32Array` views over `memory.buffer` at the pointers the sim exposes.
- **Gotcha:** when WASM memory grows, `memory.buffer` is replaced and every old view is detached. Re-create the views whenever `memory.buffer !== lastBuffer`, and check this once per frame. Reserve generously at battle start, so growth is rare.

**Rust to TypeScript, events:**
- Hits, volleys, falls, house_fall, banner_fall, freed and so on go into a packed `Uint32`/`Float32` event ring.
- Each frame TypeScript drains it. Sound and the view both consume it.

**TypeScript to Rust, orders:**
- `apply(tick, team, deed_json)`. JSON at this boundary is fine, since there are only a few orders per minute.
- The queue lives in Rust, so a replay is the seed plus the log, natively and in the browser.

**TypeScript to Rust, stepping:**
- `step(n)` advances n fixed ticks of 1/30 s.
- TypeScript owns the accumulator, the time scale (×0.3 while drawing or speaking) and pause.

**Land:**
- `Land::make(map_json, seed)` returns:
  - the RGBA ground texture
  - the height grid
  - tree, rock and bush instance arrays
- Call it in a Web Worker that loads the same WASM module, and transfer the buffers to the main thread (`03-land.md` §10). In Rust it may be fast enough on the main thread; measure it on day 2.

The data shapes are defined in `contracts/contracts.rs` and mirrored in `contracts/contracts.ts`. **Agree on these before splitting work.**

### Determinism rules for the Rust sim
- **Randomness:** only `hash32(seed, id, salt)` and the xorshift32 `Rng` from `03-land.md` §2. Nothing else.
- **Math:** `libm::{sin, cos, atan2, exp, pow, hypot}`. Basic float operations and `sqrt` are IEEE-exact. Never use `f64::sin` and friends, which call the platform's math library.
- **Iteration order:**
  - No `HashMap` or `HashSet` iteration anywhere in the sim. Use `Vec` indexed by id, or `BTreeMap`.
  - Sort with `total_cmp` and a tie-break on id.
- **Execution:** no threads or `rayon` inside a tick. One `f64` time base: tick count × (1/30).
- **Check:** a test runs the same seed and log natively and in WASM (via `wasm-pack test --node`) and compares state hashes every 300 ticks.

### Toolchain (on your M5 Pro, 64 GB)
Already installed: `rustc`, `cargo`, `node` (via mise).

Install:
```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-pack          # or: brew install wasm-pack
brew install llama.cpp whisper-cpp ffmpeg
```

Crates (pin the exact versions in Cargo.lock on day 1):
- `wasm-bindgen 0.2`
- `js-sys`
- `serde` + `serde_json`
- `libm 0.2`
- harness: `clap 4`, `image 0.25`

Web: `three ^0.180.0`, `vite ^6`, `typescript ^5.7`, the same versions the original shipped with.

**Building the WASM:**
```bash
wasm-pack build crates/sim-wasm --target web --out-dir ../../web/src/sim-pkg --release
```
Then in TypeScript: `import init, { Battle } from './sim-pkg/sim_wasm.js'; await init();`.

A `npm run sim` script wraps the build. During development, run `cargo watch -x 'run -p harness -- …'` for the rules and Vite for the view.

**Hosting:**
- Vercel or Cloudflare Pages serve `.wasm` as `application/wasm` by default.
- Keep the cache headers from `01-flow.md` §8 (hashed assets immutable for a year; `index.html` must revalidate).

### Glimmer on this machine
64 GB of unified memory runs a 4-bit 30B model comfortably. Use the M5 Pro's GPU through llama.cpp (Metal) or MLX. **Measure with `voice-eval` on day 1** (`06-voice.md` §9 and `../06-voice-eval/`).

## If you still want a Rust renderer later
After the hackathon, Bevy (wgpu, with WebGL2 and WebGPU backends) would be the natural home. The sim crate drops in unchanged as a Bevy plugin, because it was never tied to the view. That is one more reason to keep the boundary clean now.
